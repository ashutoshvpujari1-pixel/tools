What does SOLID mean?

SOLID is a set of five guidelines for designing object-oriented software. They are not strict laws; they are useful ways to avoid code that becomes difficult to change.

Think of building a house: give each room a clear purpose, allow extensions without rebuilding everything, and make sure parts can be swapped for compatible alternatives.

Why use SOLID?

  • Changes are less likely to break unrelated code.
  • Features are easier to add.
  • Classes are easier to test.
  • Responsibilities are clearer to teammates.

Remember: do not add extra classes or interfaces just to follow a rule. Keep the design as simple as the problem allows.

The five principles, one by one

S

Single Responsibility Principle (SRP)

One class should have one main reason to change.

In simple language: give a class one clear job. A class that calculates an invoice should not also print it and email it.

❌ Before — too many jobs

Invoice calculates totals, prints the invoice, and sends emails. A change to email delivery forces you to edit the invoice class.

✅ After — separate jobs

Invoice holds invoice data; InvoicePrinter prints it; InvoiceEmailer sends it.

Java example
class Invoice {
    private final double amount;

    Invoice(double amount) {
        this.amount = amount;
    }

    double total() {
        return amount * 1.18; // example: add 18% tax
    }
}

class InvoicePrinter {
    void print(Invoice invoice) {
        System.out.println("Invoice total: " + invoice.total());
    }
}

class InvoiceEmailer {
    void email(String customerEmail, Invoice invoice) {
        System.out.println("Emailing invoice to " + customerEmail);
    }
}
Easy memory trick: one class = one main job. If you describe a class using “and” many times, check whether it has too many responsibilities.
O

Open/Closed Principle (OCP)

Open for adding new behavior, closed for repeatedly changing working code.

In simple language: when a new requirement arrives, try to add a new implementation instead of editing a long chain of existing if/else statements.

❌ Fragile approach

A payment method has a long if/else for card, UPI, wallet, and every future payment type. Every new option changes the same class.

✅ Extend with a new class

Define a common PaymentMethod contract. Each payment type implements it; adding another type usually means adding a class.

Java example
interface PaymentMethod {
    void pay(double amount);
}

class UpiPayment implements PaymentMethod {
    public void pay(double amount) {
        System.out.println("Paid by UPI: " + amount);
    }
}

class CardPayment implements PaymentMethod {
    public void pay(double amount) {
        System.out.println("Paid by card: " + amount);
    }
}

class Checkout {
    void complete(PaymentMethod method, double amount) {
        method.pay(amount);
    }
}

// To add WalletPayment, create another class
// implementing PaymentMethod. Checkout stays unchanged.
Easy memory trick: add a new option by extending the design, not by constantly rewriting stable code.
L

Liskov Substitution Principle (LSP)

A subtype should work wherever its parent type is expected.

In simple language: if code expects a Bird that can fly, do not make every bird inherit from that type—because a penguin cannot fly. Model only what is true for all members of a type.

❌ Broken expectation

A Penguin extends a FlyingBird class but throws an error when fly() is called. Code using FlyingBird cannot safely use every subtype.

✅ Model capabilities correctly

Use a general Bird type and a separate Flyable capability. Only birds that can fly implement it.

Java example
interface Bird {
    void eat();
}

interface Flyable {
    void fly();
}

class Sparrow implements Bird, Flyable {
    public void eat() {
        System.out.println("Sparrow eats seeds");
    }

    public void fly() {
        System.out.println("Sparrow flies");
    }
}

class Penguin implements Bird {
    public void eat() {
        System.out.println("Penguin eats fish");
    }
}

// A method that needs flight accepts Flyable,
// so Penguin is never passed to it by mistake.
class FlightLesson {
    void demonstrateFlight(Flyable bird) {
        bird.fly();
    }
}
Easy memory trick: a child class must keep the promises made by its parent type. Do not promise behavior that some child objects cannot provide.
I

Interface Segregation Principle (ISP)

Prefer small, focused interfaces over one giant interface.

In simple language: do not force a class to implement methods it does not need. A basic printer should not be forced to scan or fax.

❌ Too broad

One OfficeMachine interface requires print(), scan(), and fax(). A printer that only prints must provide fake or unsupported methods.

✅ Small interfaces

Separate Printer, Scanner, and Fax capabilities. Each device implements only what it can actually do.

Java example
interface Printer {
    void print(String document);
}

interface Scanner {
    void scan(String document);
}

class BasicPrinter implements Printer {
    public void print(String document) {
        System.out.println("Printing: " + document);
    }
}

class MultiFunctionPrinter implements Printer, Scanner {
    public void print(String document) {
        System.out.println("Printing: " + document);
    }

    public void scan(String document) {
        System.out.println("Scanning: " + document);
    }
}
Easy memory trick: many small, specific promises are better than one huge promise that every class must keep.
D

Dependency Inversion Principle (DIP)

High-level business logic should depend on abstractions, not on a specific tool.

In simple language: your order service should ask for a notification service, not be permanently tied to one email provider. Then you can switch to SMS or another email provider more easily.

❌ Tightly coupled

OrderService directly creates a specific email sender using new. Replacing that sender means changing the business logic.

✅ Depend on a contract

OrderService receives a Notifier. Any class that implements the interface can be supplied, which also makes testing easier.

Java example
interface Notifier {
    void send(String message);
}

class EmailNotifier implements Notifier {
    public void send(String message) {
        System.out.println("Email: " + message);
    }
}

class SmsNotifier implements Notifier {
    public void send(String message) {
        System.out.println("SMS: " + message);
    }
}

class OrderService {
    private final Notifier notifier;

    OrderService(Notifier notifier) {
        this.notifier = notifier;
    }

    void placeOrder() {
        System.out.println("Order placed");
        notifier.send("Your order is confirmed");
    }
}

// Example use:
// OrderService service = new OrderService(new EmailNotifier());
// service.placeOrder();
// Swap EmailNotifier for SmsNotifier when needed.
Easy memory trick: depend on what a component can do (an interface), not on the exact component that does it. Passing dependencies in through a constructor is called dependency injection.

One-minute revision

  • S: one class, one main responsibility.
  • O: add new behavior with extensions where practical.
  • L: subtypes should honor the expectations of their parent type.
  • I: keep interfaces small and focused.
  • D: business logic depends on abstractions, not concrete tools.

These examples are teaching illustrations, not complete production payment, invoicing, or notification systems.
